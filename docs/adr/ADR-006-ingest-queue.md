# ADR-006. Черга прийому подій на Redis Streams

- **Статус:** ухвалено (PR #41, ACKEE-18, злито 2026-10-23)
- **Дата:** 2026-10-22
- **Тікет:** ACKEE-18 (US-D1, епік EP-D); підготовка до ACKEE-19 (окремі процеси API / ingest / worker)
- **Оновлено:** 2026-10-25, ACKEE-84 (рев'ю PR #41): touch невідомого запису – 3 доставки без логу на
  кожну, fallback-запис знеособлює, як воркер

## Контекст

Кожна подія трекера (перегляд і оновлення тривалості кожні 15 с) пишеться в MongoDB прямо в
резолвері. Коли хтось відкриває важкий звіт, база зайнята, і трекер чекає на відповідь разом
із нею. Картка вимагає: подія підтверджується одразу, без Redis сервер працює як раніше,
повторна доставка нічого не дублює. ADR-005 залишив ризик «Черга прийому»: печатка годин
має враховувати події, які ще не записані.

## Варіанти

- **Писати напряму, як зараз.** Прийом і далі залежить від навантаження бази.
- **Буфер у пам'яті процесу.** Події губляться при падінні процесу, а ACKEE-19 рознесе API
  і запис по різних процесах.
- **Redis Streams з групою споживачів.** Підтвердження після запису, повторна доставка
  непідтвердженого, Redis уже є в стеку (`ACKEE_REDIS` для солі). Обрано.

## Рішення

**Потік.** API робить усі перевірки, як зараз (ігнорування своїх візитів, домен, ingest key і
origin, нормалізація, валідація схеми без MongoDB), рахує `clientId`, сам призначає `id`,
`created = updated = час запиту`, кладе подію в stream `ackee:ingest` (`XADD`) і відповідає
трекеру тим самим payload, що й без черги. Воркер у тому самому процесі (`src/index.js`, поруч
зі згортками) читає stream групою `ackee-ingest` і пише в MongoDB:
`XAUTOCLAIM` (min-idle 60 с) → `XREADGROUP … COUNT 200 BLOCK 1000` → запис по черзі →
`XACK` + `XDEL` у `MULTI`. ACKEE-19 рознесла API і воркер по процесах: `ACKEE_ROLE=api` чи `ingest`
лише кладе події в stream, `ACKEE_ROLE=worker` лише пише з нього; без змінної все в одному процесі, як тут описано.

**Змінні.** `ACKEE_INGEST_QUEUE=<redis URL>` вмикає чергу, порожнє значення – як не задане.
`ACKEE_INGEST_CONSUMER` – ім'я споживача, за замовчуванням ім'я хоста. `src/serverless.js`
із заданою чергою не стартує: функція живе один запит, воркеру ніде працювати.

**Окремий Redis.** Сіль (`ACKEE_REDIS`) – Redis без persistence, черга – з AOF.
Persistence налаштовується на весь інстанс, тож це два інстанси: старт падає, якщо host:port
черги і солі збігаються (`localhost`, `127.0.0.1` і `::1` – один хост). Черга – з
`maxmemory-policy noeviction`, тож переповнений Redis відмовляє в `XADD`, а не викидає те, що
чекає. `MAXLEN` на stream не ставимо: обрізання губило б незаписані події.

**З'єднання** (`src/queue/redis.js`). Два клієнти `@redis/client`: для API (`XADD`, метрики,
печатка) і для воркера – блокуюче читання тримає з'єднання, і трекер чекав би на нього.
`disableOfflineQueue`: поки Redis недоступний, команди падають одразу, а не чекають
перепідключення. Перше звернення чекає першої спроби з'єднання, щоб перша подія процесу не
йшла в обхід черги лише через те, що з'єднання ще відкривається. Втрату з'єднання видно в лозі
один раз на збій.

**Дедлайн API.** Тайм-аут команди в `@redis/client` діє, лише поки команда чекає на відправку:
записану в сокет команду живий, але завислий Redis (`CLIENT PAUSE`, довгий `DEBUG SLEEP`)
тримає скільки завгодно. Тому `enqueue`, `length` і `oldest` мають власний дедлайн на весь
виклик, разом з очікуванням з'єднання: `INGEST_ENQUEUE_TIMEOUT`, 1 с. Після нього подія йде
напряму з `reason="unavailable"`, а scrape і побудова згорток отримують помилку, а не висять і
не накопичуються. `XADD`, що дійде пізніше, лишить подію і в черзі; воркер побачить дубль
ключа, тобто успіх. Воркер дедлайну не має: при завислому Redis він просто чекає, а
неписані події лишаються в черзі.

**Кеш доменів.** Із чергою `createRecord` бере домен із кешу на 30 с
(`domains.getUnscopedCached`, `src/utils/cachedLookup.js`, `INGEST_DOMAIN_TTL`): без нього API
все одно ходить у MongoDB під важким звітом. Запис, старший за 30 с, ще 30 с віддається
одразу, а один спільний запит оновлює його у фоні, тож прийом не чекає на MongoDB і раз на
30 с. Старший за 2 × 30 с запис не віддається: виклик чекає на свіже значення, і помилка
MongoDB тоді доходить до трекера. Без цієї межі домен, який годину не мав переглядів, один раз
пропустив би подію зі старим ключем. Чекає також перший запит домену, якого в кеші ще немає.
Оновлення, що нічого не знайшло, прибирає запис; помилка оновлення лишає старе значення, і
наступний виклик пробує знову. Відсутній домен і помилки
першого читання не кешуються, тож випадкові id не займають пам'ять.

`updateDomain`, `rotateIngestKey` і `deleteDomain` скидають запис кешу в тому ж процесі (у
`src/database/domains.js`, тож це не залежить від резолвера). Тому в межах процесу новий ключ,
strict mode, title чи видалення діють одразу, як без черги. З кількома процесами (ACKEE-19)
інші процеси бачать зміну протягом 2 × 30 с: старий ключ ще до хвилини проходить там, а події
видаленого домену воркер відкидає (`unknown_domain`). Без черги кешу немає.

**Redis недоступний або переповнений** – подія пишеться напряму, з тим самим `id` і датами,
а `ackee_ingest_fallback_total{reason}` рахує її (`unavailable` / `full`, OOM). Перегляд
пишеться тим самим кодом, що й у воркера (`records.addOnce`, див. «Ідемпотентність»), а не
як без черги: поки API чекав Redis, воркер міг уже записати новіший перегляд того ж
відвідувача, і знеособлення «всіх, крім себе» забрало б відвідувача в новішого. Якщо `XADD`
таки дійшов, але відповідь запізнилася, подія буде і в базі, і в черзі; хто з двох запише
другим, побачить дубль ключа, тобто успіх. Touch іде напряму, як без черги. Лог – один рядок
на хвилину для кожної причини.

**Що йде в чергу.** Лише перегляди: `createRecord` → `record.create`, `updateRecord` →
`record.touch { id, updated }`. Дії (`createAction` / `updateAction`) лишаються прямими – ACKEE-18b.

**Повідомлення** (`src/queue/messages.js`): поля `v` (версія формату, зараз `1`), `type`, `at`
(час, коли API прийняв подію, мс) і `data` (JSON). У `data` є `clientId`, але немає IP і
user agent, з яких його пораховано.

**Ідемпотентність** (`src/queue/worker.js`, `src/database/records.js`):

- `record.create` – `records.addOnce`: `Record.create` з `id` і датами з повідомлення. Дубль
  ключа (11000) – це успіх: запис зробила попередня доставка, яка не дожила до підтвердження,
  або API, коли `XADD` запізнився. Анонімізація попередніх записів відвідувача повторюється, бо
  та доставка могла впасти між двома записами. Знеособлюються лише записи, не новіші за подію;
  див. «Порядок подій одного відвідувача».
- Дати події (`created`, `updated`) беруться лише з повідомлення; повідомлення без них
  відкидається як `malformed`.
- `record.touch` – `updated` через `$max`, тож повторне чи запізніле оновлення не повертає час
  назад. Прямий шлях теж іде через `$max` з поточним часом – результат той самий.
- Підтвердження (`XACK` + `XDEL` у `MULTI`) – лише після запису. Підтверджене одразу видаляється,
  тож у stream лежить тільки те, що ще не записано.

**Помилки.**

| Що сталося                                                                                                            | Що робить воркер                                                                                                             |
| --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| MongoDB чи Redis недоступні, будь-яка невідома помилка                                                                | Батч зупиняється, записане підтверджується, решта лишається в черзі; повтор через 5 с, спершу непідтверджене                 |
| Повідомлення, яке не записати ніколи (`ValidationError`, `CastError`, невідомі `v` чи `type`, битий JSON, немає `id`) | Лог `error` на кожне, лічильник `ackee_ingest_queue_dropped_total{reason}`, підтвердження. Окремого dead-letter stream немає |
| Подія домену, видаленого, поки вона чекала                                                                            | Так само, `reason="unknown_domain"`. Домени батча перевіряються одним запитом                                                |
| `record.touch` без свого запису: обігнав `record.create` (лише при повторній доставці) або `id` вигаданий             | Мовчки лишається в черзі; на 3-й доставці (≈ 2 хв) відкидається, `reason="unknown_record"`, лог – рядок на хвилину           |

Чому вистачає 3 доставок (`INGEST_MAX_DELIVERIES`). Трекер шле touch лише після відповіді на
create, тож create стоїть у stream раніше. Обігнати його touch може, лише коли create завис у
PEL мертвого чи повільного споживача. Такий create забирається `XAUTOCLAIM` через
`INGEST_MIN_IDLE` (60 с), а touch – не раніше, бо його видали пізніше; у батчі claim записи
йдуть за id, create перед touch. Тож друга доставка зазвичай уже знаходить запис, третя – запас
на кілька споживачів (ACKEE-19) і збій між ними. Touch вигаданого `id` живе в Redis
(N − 1) × `INGEST_MIN_IDLE`: перша доставка, далі кожна через `XAUTOCLAIM` щохвилини. Тобто
≈ 2 хв замість ≈ 4 з колишніми 5 доставками.

`updateRecord` не потребує входу, тож такий touch може слати будь-хто. Тому до останньої
доставки воркер нічого не пише в лог, а відкинуті `unknown_record` зводить в один рядок на
хвилину з кількістю за цей час (на процес, як і збої циклу). Лічильник
`dropped_total{reason="unknown_record"}` рахує кожен. Решту причин відкидання звичайним запитом
до API не створити: це баги або чужий запис у stream, тож кожна – окремий рядок.

Лічильник доставок веде Redis, і він росте від кожної видачі запису: `XREADGROUP >`,
`XAUTOCLAIM` і читання власного PEL (`XREADGROUP` з id) після рестарту чи збою. Тому межа в
3 доставки рахує і такі повтори, див. ризики.

Збій воркер пише в лог `error` одразу, далі не частіше рядка на хвилину на тип збою (батч чи
сам цикл і назва помилки), хоча повторює щоп'ять секунд.

Невідома помилка навмисно не вважається отруйною: краще, щоб черга голосно стала, ніж тихо
губила події.

**Печатка згорток** (ризик ADR-005). `sealedUntil(now, pendingSince)` рахує межу так, ніби час
ще той, що в найстарішої події черги: `sealedUntil(min(now, oldest))`, де `oldest` – `at` першого
запису stream (`XRANGE - + COUNT 1`; підтверджене видаляється, тож перший запис – найстаріший
незаписаний). Якщо черга ввімкнена, але Redis недоступний, побудова згорток пропускається
(`src/utils/rollupJob.js`).

**Споживачі.** Один споживач на процес, з ім'ям хоста (або `ACKEE_INGEST_CONSUMER`), а не
`hostname-pid`: процес після рестарту з тим самим ім'ям на старті одразу читає власний PEL
(`XREADGROUP … 0`), не чекаючи хвилини на `XAUTOCLAIM`. Так само після збою: воркер спершу
проходить власні непідтверджені записи, а не знижує min-idle для всіх (інакше на ACKEE-19
він забирав би записи живих сусідів). Те, що лишив процес з іншим ім'ям, забирає будь-хто
через `XAUTOCLAIM` після 60 с. Мертві споживачі видаляються `XGROUP DELCONSUMER` раз на
10 хв: лише ті, хто не з'являвся годину і нічого не тримає. Видалення споживача викидає його
PEL, а ці записи вже ніхто не доставить, тому перевірка й видалення йдуть одним Lua-скриптом.

**Метрики** (`/metrics`). Gauges `ackee_ingest_queue_length` (`XLEN`) і
`ackee_ingest_queue_oldest_age_seconds` читаються з Redis на кожен scrape; без черги – `0` без
з'єднання, при недоступному Redis лишається останнє значення. Counters
`ackee_ingest_queue_processed_total{type}`, `ackee_ingest_queue_dropped_total{reason}`,
`ackee_ingest_fallback_total{reason}` – лічильники процесу, усі відомі мітки від нуля.

**Що трекер більше не дізнається.** Із чергою `updateRecord` для невідомого `id` відповідає
`success`: запис може ще чекати в черзі, а відкинутий touch видно в
`dropped_total{reason="unknown_record"}` і в зведеному рядку логу раз на хвилину. Помилки
`createRecord` (невідомий домен, ключ, origin, валідація) – ті самі, що без черги.

**Тести.** Логіка воркера – з фейковим адаптером і MongoDB у пам'яті (`test/queue/worker.js`).
Адаптер і шлях GraphQL → черга → воркер → MongoDB – зі справжнім Redis за `ACKEE_TEST_REDIS`
(`test/queue/redis.js`, `test/resolvers/ingestQueue.js`); у CI це job Coverage із сервісом
`redis:7.4-alpine`. Обхід черги при недоступному Redis і «без змінної як раніше» перевіряються
без Redis, у кожному job.

**Без `ACKEE_INGEST_QUEUE`** клієнт Redis не створюється, і все працює як до цього ADR.
Порожнє значення теж вимикає чергу.

## Наслідки

- Трекер отримує відповідь до запису в базу; звіти бачать подію лише після того, як воркер
  її запише.
- Звіти поточної доби читають записи, тож відставання черги видно як відставання цифр, а не
  як помилку. Згортки його враховують через печатку.
- ACKEE-19 лише рознесе API і воркер по процесах: формат повідомлень і правила доставки ті самі.
- Під час збою Redis прийом працює як без черги – і так само залежить від навантаження бази.
- Два процеси з однаковим ім'ям хоста (наприклад, два `npm run server` на одній машині) ділять
  одного споживача й можуть записати подію двічі; запис ідемпотентний, але краще задати
  `ACKEE_INGEST_CONSUMER`.

## Ризики

- **Приватність AOF.** Поки подія в черзі, в AOF лежить неанонімізований запис (`clientId` і поля
  пристрою). Потрібна згода PO; заходи – виключити дані Redis черги з бекапів і частіше робити
  AOF rewrite.
- **Порядок подій одного відвідувача.** Непідтверджене повідомлення мертвого споживача
  забирається через `XAUTOCLAIM` лише через хвилину, тож старіший `record.create` може прийти
  після новішого того ж `clientId`. Тому воркер знеособлює лише записи, не новіші за подію
  (`created <= data.created`, крім самого запису), а якщо новіший запис уже є – знеособлює сам
  поточний. Перегляди однієї мілісекунди рахуються як старші, тож незнеособленим лишається рівно
  один запис. Інваріант не залежить від імені споживача.
- **Вікно втрати.** З `appendfsync everysec` при падінні Redis можна втратити до 1 с уже
  підтверджених трекеру подій.
- **Вимкнення черги з відставанням.** Спершу дочекатися нуля в черзі, потім знімати змінну:
  без неї воркер не стартує, і події, що лишилися в stream, ніхто не запише.
- **Touch під час збою Redis.** Touch, що пішов напряму, поки його `record.create` ще чекає в
  черзі, не знаходить запису й губиться: тривалість цього візиту буде коротшою.
- **Ліцензія Redis 7.4** (RSAL/SSPL). Valkey – заміна без зміни коду: потрібні лише Streams і
  Lua.
- **Зміни домену в кількох процесах.** Після ACKEE-19 ротація ключа чи ввімкнення strict mode
  діє в інших процесах API лише через до 2 × 30 с (хвилину). Якщо цього мало, потрібне
  скидання кешу через Redis (pub/sub) – окремим тікетом.
- **Неавтентифікований touch** (рев'ю PR #41, ACKEE-84). Touch вигаданих `id` і далі займає
  Redis ≈ 2 хв кожен, лише приблизно вдвічі менше, ніж ≈ 4 хв з 5 доставками: масовий флуд
  при `maxmemory` і `noeviction` усе ще може переповнити Redis черги, і тоді події йдуть
  напряму (`full`). Лог він уже не заливає. Повний захист – обмеження частоти `updateRecord` або перевірка існування
  запису на API – поза ACKEE-84, окремою карткою, якщо команда вирішить. Флуд видно з
  `ackee_ingest_queue_length` і `ackee_ingest_queue_dropped_total{reason="unknown_record"}`.
- **Лічильник доставок рахує й повтори.** `XREADGROUP` з id (читання власного PEL на старті й
  після кожного збою) теж збільшує лічильник доставок, як і `XAUTOCLAIM`. Тож
  `INGEST_MAX_DELIVERIES = 3` – це «3 доставки або повтори»: touch, що чекає свого create,
  може бути відкинутий (`unknown_record`) раніше, якщо поруч були збої. На ACKEE-19 з кількома
  воркерами і частими рестартами це помітніше; тоді варто рахувати спроби самому або підняти
  межу.
