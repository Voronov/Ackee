# Стенд для вимірів

Локальний стенд з 10 млн записів, на якому міряємо швидкість звітів. Базовий замір v1.0 нижче –
точка відліку для індексу в MongoDB (ACKEE-7, ACKEE-8) і для ClickHouse (ACKEE-15, ACKEE-17).
Нові заміри порівнюємо з ним на тій самій машині й з тими самими лімітами.

## Склад

Файл `docker-compose.bench.yml`, проєкт `ackee-bench`. Контейнери й томи мають префікс
`ackee-bench`, порти – інші, ніж у розробки, тож стенд не зачіпає локальні `ackee-mongo`,
`ackee-clickhouse` і їхні томи.

| Сервіс       | Профіль      | Порт на хості | Ліміт пам'яті | Що це                                                                    |
| ------------ | ------------ | ------------- | ------------- | ------------------------------------------------------------------------ |
| `mongo`      | –            | 27018         | 3 GiB         | `mongo:7`, кеш WiredTiger 1.5 GB, том `ackee-bench-mongo-data`           |
| `ackee`      | –            | 3100          | 1 GiB         | образ `ackee-bench-ackee:local` з поточного коду, вхід `bench` / `bench` |
| `seed`       | `seed`       | –             | 1 GiB         | одноразовий засів `scripts/seed-records.js`                              |
| `clickhouse` | `clickhouse` | 8124          | 2 GiB         | `clickhouse/clickhouse-server:24.8`, лише для перевірки пам'яті          |

Ліміти, порти, кеш і паролі змінюються змінними `BENCH_*` (див. значення `${BENCH_*:-…}` у
файлі):

| Змінна                      | За замовчуванням | Що це                         |
| --------------------------- | ---------------- | ----------------------------- |
| `BENCH_MONGO_PORT`          | 27018            | порт MongoDB на хості         |
| `BENCH_MONGO_MEMORY`        | 3g               | ліміт пам'яті `mongo`         |
| `BENCH_MONGO_CACHE_GB`      | 1.5              | кеш WiredTiger, GB            |
| `BENCH_ACKEE_PORT`          | 3100             | порт Ackee на хості           |
| `BENCH_ACKEE_MEMORY`        | 1g               | ліміт пам'яті `ackee`         |
| `BENCH_ACKEE_USERNAME`      | bench            | `ACKEE_USERNAME` стенда       |
| `BENCH_ACKEE_PASSWORD`      | bench            | `ACKEE_PASSWORD` стенда       |
| `BENCH_SEED_MEMORY`         | 1g               | ліміт пам'яті `seed`          |
| `BENCH_CLICKHOUSE_PORT`     | 8124             | HTTP-порт ClickHouse на хості |
| `BENCH_CLICKHOUSE_MEMORY`   | 2g               | ліміт пам'яті `clickhouse`    |
| `BENCH_CLICKHOUSE_PASSWORD` | bench            | пароль користувача `default`  |

Кеш WiredTiger задано явно, щоб результат не залежав від обсягу пам'яті машини.

## Підняти

```sh
docker compose -f docker-compose.bench.yml up -d --build
```

Образ бере зібраний інтерфейс із закомічених `dist/*`. Звіти міряємо через API, тому
`npm run build:pre` перед збіркою необов'язковий. Він переписує tracked-файли в `dist/` – їх
не комітимо (`git checkout dist`).

## Засіяти

```sh
docker compose -f docker-compose.bench.yml --profile seed run --rm seed
```

За замовчуванням – 10 млн записів за 60 днів, `--seed 42`, пачки по 5000, у новий домен
`Seed 10000000 records`. Профіль ЛР-1: ≈2 % унікальних відвідувачів (200 тис.), 300 сторінок,
150 реферерів, тож у вікні 30 днів ≈5 млн записів.

Дані такі, якими їх лишає справжній трекер:

- записи вставляються в порядку `created`, рівномірно за весь період;
- `clientId` міняється щодня. Трекер о 00:00 за часом сервера бере нову сіль
  (`src/utils/salt.js`); контейнер стенда працює в UTC, тож межі доби генератор бере в UTC.
  Пара «відвідувач + доба (UTC)» має власний `clientId`;
- анонімізація відтворена в межах цієї пари: `clientId` і поля, які обнуляє
  `records.anonymize` (`src/database/records.js`), – мова, екран, пристрій, система, браузер –
  лишаються лише в останньому за `created` записі відвідувача за добу. В решти вони `null`, як
  після `updateMany`.

З профілем ЛР-1 відвідувач у середньому має 50 записів за 60 днів і заходить у ≈34 різні доби,
тож `clientId` зберігають ≈68 % записів. Це наслідок моделі: відвідувач вибирається рівномірно,
на пару «відвідувач + доба» припадає ≈1.5 перегляду. На живих сайтах (2–3 перегляди за візит)
частка зазвичай менша, 33–50 %, а від неї залежить план `UNIQUE`.

Параметри – змінні `SEED_RECORDS`, `SEED_DAYS`, `SEED_SEED`, `SEED_BATCH`, `SEED_DOMAIN`,
`SEED_NOW`; решта аргументів передається генератору як є:

```sh
docker compose -f docker-compose.bench.yml --profile seed run --rm seed --dry-run
```

З хоста – лише з явною адресою бази стенда. Без неї `npm run seed` бере `ACKEE_MONGODB` з
`.env` і пише в базу розробки:

```sh
ACKEE_MONGODB=mongodb://127.0.0.1:27018/ackee npm run seed -- --records 10000000 --days 60 --seed 42
```

Відтворюваність: конкретні записи залежать від `--seed` і id домену, а id нового домену щоразу
випадковий. На іншому стенді записи інші, але розподіл, порядок і частка анонімізованих записів
ті самі – для замірів цього досить. Побітово однаковий датасет дає лише засів у той самий
домен (`SEED_DOMAIN`).

Повторний засів додає ще один домен поруч. Щоб почати з нуля, стенд прибирають з `-v`
(див. «Прибрати»).

Записи відраховуються від моменту засіву (`--now`, за замовчуванням – зараз). Вікно «останні
30 днів» з часом з'їжджає: через 15 днів у ньому лишиться половина даних. Для порівняння з
базовим заміром стенд засівають наново.

## Заміряти

```sh
docker compose -f docker-compose.bench.yml restart mongo ackee   # холодний кеш WiredTiger, як у базовому замірі
npm run measure
```

`scripts/measure-reports.js` логіниться в Ackee стенда, знаходить єдиний домен і по черзі
надсилає запити дашборда за 30 днів – кожен окремо, без паралельного навантаження:

- `views(interval: DAILY, type: UNIQUE, limit: 30)`
- `views(interval: DAILY, type: TOTAL, limit: 30)`
- `referrers(sorting: TOP, type: WITH_SOURCE, range: LAST_30_DAYS)`
- `durations(interval: DAILY, limit: 30)` – дашборд просить 14 днів, 30 – для однакового вікна з
  іншими звітами. У стовпці «Result» – середнє денних тривалостей.

Кожен звіт – `--runs` разів (за замовчуванням 3), у таблиці – медіана, мінімум і максимум
успішних запусків і кількість невдалих. Таблиця виходить у Markdown, її можна вставити нижче.

| Опція         | За замовчуванням        | Що це                                                                       |
| ------------- | ----------------------- | --------------------------------------------------------------------------- |
| `--url`       | `http://127.0.0.1:3100` | Ackee стенда                                                                |
| `--username`  | `bench`                 | `ACKEE_USERNAME` стенда                                                     |
| `--password`  | `bench`                 | `ACKEE_PASSWORD` стенда                                                     |
| `--domain`    | єдиний домен            | обов'язкова, коли доменів кілька                                            |
| `--report`    | усі чотири              | `views-unique`, `views-total`, `referrers`, `durations`; можна кілька разів |
| `--runs`      | 3                       | повторів на звіт                                                            |
| `--timeout`   | 60                      | хвилин очікування відповіді на один запит                                   |
| `--time-zone` | `UTC`                   | заголовок `Time-Zone`, як у дашборда                                        |
| `--unit`      | `s`                     | `s` або `ms` – одиниця часу в таблиці; `ms` для звітів, швидших за 0.1 с    |

Клієнт працює через `node:http`, а не `fetch`: `fetch` (undici) обриває відповідь, якої немає
300 с. Сервер Ackee довгий запит сам не обриває: `requestTimeout` Node (300 с) стосується лише
отримання запиту, а не відповіді, – у першому замірі запити по 41 хв дійшли до кінця.
Невдалий запит – теж результат: він потрапляє в стовпець «Failed» з причиною.

Після таймауту клієнта замір зупиняється. Ackee не скасовує агрегацію, коли клієнт відключився,
тож MongoDB рахує її далі, і кожен наступний запуск конкурував би з нею. Перед повтором стенд
перезапускають (`restart mongo ackee`).

Пам'ять під час заміру – `docker stats` у сусідньому терміналі, разом із ClickHouse:

```sh
docker compose -f docker-compose.bench.yml --profile clickhouse up -d clickhouse
docker stats $(docker ps --format '{{.Names}}' | grep '^ackee-bench')
```

## Результати

Очікування «≈188 с» з картки стосується звіту `durations`: ADR-004 (гілка
`feature/clickhouse-ingest`, `docs/adr/ADR-004-clickhouse.md`) наводить для нього 179.5 і
188.9 с на 10 175 059 записах, на холодному кеші. Машина й ліміти того заміру в репозиторії не
зафіксовані. Тож з ≈188 с порівнюємо лише `durations`, і лише орієнтовно. Точка відліку – v1.0
нижче.

**Критерій «є базовий замір v1.0» – виконано:**

- `durations` – 13.0 с проти ≈188 с в ADR-004 гілки `feature/clickhouse-ingest`, у ≈14 разів
  швидше. Умови різні (машина, ліміти, датасет), тож це орієнтир, а не порівняння версій.
- `views` і `referrers` – ≈9–10 с. З ≈188 с їх не порівнюємо: те число стосувалося іншого звіту.
  Числа ADR-004 гілки `feature/clickhouse-ingest` для них (p95 31 і 21 с) зняті під
  навантаженням 10 користувачів, тож з одиночними запитами теж не порівнюються.

Аргумент для ClickHouse (ACKEE-15, ACKEE-17) на цих цифрах звучить інакше. «`durations` іде
≈3 хв» на стенді не підтвердилось. Лишається інше: кожен із чотирьох звітів читає ≈5 млн
документів вікна і займає 9–13 с, що далеко від NFR ≤ 300 мс з ADR-004 гілки
`feature/clickhouse-ingest`. Оцінювати ClickHouse слід відносно цих 9–13 с і цього NFR, з
урахуванням реалістичнішої частки записів з `clientId` (див. «Засіяти»).

Пікова пам'ять (`docker stats` кожні 5 с):

| Контейнер                | Пік      | Ліміт | Примітка                                   |
| ------------------------ | -------- | ----- | ------------------------------------------ |
| `ackee-bench-mongo`      | 1672 MiB | 3 GiB | ліміт не досягнуто (`memory.events max` 0) |
| `ackee-bench-ackee`      | 141 MiB  | 1 GiB |                                            |
| `ackee-bench-clickhouse` | 522 MiB  | 2 GiB | порожній, без даних                        |

У серії `durations` пік `ackee-bench-mongo` – 1698 MiB, `ackee-bench-ackee` – 172 MiB,
`memory.events max` 0.

Що видно з даних:

- Усі чотири звіти йдуть через `IXSCAN { created: 1 }` і читають ≈5 млн документів вікна. Записи
  вікна лежать підряд, бо вставлялись за часом.
- `UNIQUE` вже не дешевший за `TOTAL`: `clientId` має більшість записів, тож планувальник не
  бере індекс `clientId` і фільтрує після читання.
- Стенд разом з порожнім ClickHouse займає ≈2.3 GiB із 7.65 GiB VM.

**Критерій «пам'яті вистачає під ClickHouse» – виконано за лімітами:** `mongo` + `ackee` +
`clickhouse` = 3 + 1 + 2 = 6 GiB, разом із `seed` – 7 GiB, менше за 7.65 GiB VM; OOM немає.
ClickHouse виміряно порожнім. Навантажений ClickHouse (10 млн рядків і запити) перевіряється в
ACKEE-15.

Проміжний замір 17.10 08:40 – той самий генератор, але один `clientId` на весь період (без
добової солі): `UNIQUE` 0.6 с через індекс `clientId` (200 тис. записів), `TOTAL` 12.0 с,
`referrers` 7.6 с. Непредставницький: без добової солі `UNIQUE` читав 200 тис. документів
замість ≈5 млн, які читає на цьому профілі.

### Перший замір, 16–17.10.2026 – непредставницький

Генератор тоді писав записи у випадковому порядку часу і без анонімізації. В тій самій VM
працювали чужі контейнери (≈2.5–3 GiB, до 40 % CPU). Ліміти й машина – ті самі.

| Report                     | Runs | Failed | Median, s | Min, s | Max, s | Result        |
| -------------------------- | ---- | ------ | --------- | ------ | ------ | ------------- |
| views DAILY UNIQUE         | 3    | 0      | 945.3     | 574.7  | 1030.3 | 4968664 views |
| views DAILY TOTAL          | 3    | 0      | 1247.6    | 778.4  | 2445.5 | 4968664 views |
| referrers TOP LAST_30_DAYS | 3    | 0      | 615.7     | 589.6  | 790.1  | 30 referrers  |

`views-unique` – окрема серія з `--timeout 20`. У ній перший `views-total` не вклався в 20 хв, і
серію зупинено. `views-total` і `referrers` – друга серія з `--timeout 60`.

Чому ці числа не годяться як точка відліку:

- **Підтверджено:** `UNIQUE` дорівнював `TOTAL` (4 968 664). Без анонімізації `clientId` був у
  кожному записі, тож «унікальні» перегляди рахували всі.
- **Підтверджено:** документи вікна були розкидані по колекції. Перші записи в природному
  порядку – з різних тижнів, план – `IXSCAN { created: 1 }`. Дані з індексами (3.6 GiB на диску)
  не вміщались у кеш 1.5 GB, MongoDB упиралась у ліміт 3 GiB (`memory.events max` ≈179 тис.,
  OOM немає).
- **Підтверджено:** у VM працювали чужі контейнери.
- **Гіпотеза:** головний внесок у різницю (`TOTAL` 1248 → 9.2 с, `referrers` 616 → 9.4 с) дає
  порядок запису: випадкове читання з диска замість послідовного. Окремо від менших документів
  і від зупинених сусідів цей внесок не міряли – все змінилося одночасно.

### Як датасет впливає на порівняння

- **MongoDB проти ClickHouse (ACKEE-15, ACKEE-17).** ClickHouse сортує дані за ключем таблиці під
  час вставки, тож від порядку вставки майже не залежить. Перший замір (випадковий порядок, без
  анонімізації, з сусідами) завищив би виграш ClickHouse на два порядки; яку частку дав саме
  порядок – не міряли. Порівнюємо лише з v1.0.
- **Складений індекс (ACKEE-7, ACKEE-8).** На хронологічних даних діапазон за `created` уже
  читається послідовно, тож від індексу на `domainId` + `created` слід чекати меншого виграшу,
  ніж підказав би перший замір. На стенді один домен, тож перевага `domainId` у складеному
  індексі тут не видна: він дає той самий діапазон, що й `{ created: 1 }`. Виграш ACKEE-7 на
  стенді – лише від покриття запиту індексом (`TOTAL` без FETCH). Для багатодоменного сценарію
  потрібен засів кількох доменів (`SEED_DOMAIN`, повторний засів) – це вирішується в ACKEE-7.
  `clientId` генератора хешується разом із `domainId`, як у `src/utils/identifier.js`, тож
  хеші між доменами не повторюються.
  Без добової солі `UNIQUE` йшов би через індекс `clientId` і виглядав би в 17 разів дешевшим,
  ніж на цьому профілі, – з таким датасетом індекс для `UNIQUE` здавався б непотрібним.
- **Гіпотеза:** кеш WiredTiger тримає сторінки розпакованими, і вікно 30 днів (≈2.3 GiB) у кеш
  1.5 GB не вміщається. Вміщаються стиснені файли вікна (≈0.9 GiB) у файловому кеші ОС у межах
  ліміту контейнера 3 GiB (пік 1672 MiB, `memory.events max` 0), тож читання йде з пам'яті, а не
  з диска. На більшому датасеті чи з меншим лімітом контейнера MongoDB знову читатиме з диска, і
  різниця з ClickHouse зросте.

Нові заміри для порівняння – на тій самій машині, з тими самими лімітами й датасетом, після
`restart mongo ackee`, без чужих контейнерів у Docker VM і без перезапуску Docker VM між засівом
і заміром. Серія після перезапуску VM (холодний і файловий кеш) – інша умова, її позначають
окремо.

## Порівняння сховищ

Спайк ACKEE-15: чотири звіти за 30 днів у чотирьох варіантах сховища на тому самому стенді й
датасеті. Рішення за цими числами – [ADR-004](../adr/ADR-004-clickhouse-decision.md).

| Варіант | Що                                                                    | Як міряли                             |
| ------- | --------------------------------------------------------------------- | ------------------------------------- |
| v1.0    | MongoDB, сирі записи, `develop`                                       | GraphQL, Ackee стенда :3100           |
| A       | MongoDB + погодинні згортки `feature/clickhouse-ingest`               | GraphQL, окремий Ackee гілки :3200    |
| A+      | A + прототип спайку: `UNIQUE` для закритих діб, `durations` sum/count | GraphQL, той самий Ackee з прапорцями |
| B       | ClickHouse, сирі таблиці (`ReplacingMergeTree` + `FINAL`)             | GraphQL :3300 і прямий SQL            |
| C       | ClickHouse + погодинні materialized views для views і referrers       | прямий SQL; `durations` – запит B     |

Код A, A+, B, C – гілка `spike/ACKEE-15-clickhouse` у Voronov/Ackee (архівна, не зливається;
база – ba11d3c1, колишня `feature/clickhouse-ingest`). Інструменти й порядок прогонів –
`tools/spike-15/README.md` у ній, сирі результати – `tools/spike-15/results/`.

| Часовий пояс | `Europe/Kiev` у всіх запитах (`--time-zone`, k6)                                                                                                                                                    |

Умова відрізняється від протоколу ACKEE-2: там сусіди були зупинені повністю, тут працюють легкі.
Тому v1.0 переміряно в тому самому блоці, і порівнюємо варіанти лише між собою, а не з 17.10.
v1.0 сьогодні повільніший, ніж 17.10 (`UNIQUE` 13.6 проти 10.3 с), хоча записів у вікні менше:
крім сусідів, у VM тепер працюють ClickHouse з даними та два Ackee гілки.

Порядок: v1.0 → A → A+ → B (GraphQL) → B і C (SQL). Перед одиночними запитами кожного варіанта –
холодний кеш його бази: `restart` MongoDB (v1.0, A, A+) або ClickHouse (B, C); файловий кеш
VM лишається теплим. Перед A і A+ `rollups-ready.js` підтвердив, що згортки покривають вікно.
Після кожного k6-прогону MongoDB перевіряли на агрегації, які клієнт покинув (`killOp`) – їх не
було.

### 10 VU, 30 с

k6 без пауз між запитами (як `report.js` з замірів 22.09): 10 одночасних запитів весь час. GraphQL –
`tools/spike-15/k6-api.sh` (ті самі запити views і referrers, що в `report.js`, плюс `TOTAL` і
`durations`), SQL – `k6-sql.sh` на запитах, які зняв `measure-sql.js`. p95 / медіана, запитів
за секунду; помилки – частка запитів з помилкою.

| Звіт          | v1.0               | A                  | A+                 | B, GraphQL                 | B, SQL                  | C, SQL                    |
| ------------- | ------------------ | ------------------ | ------------------ | -------------------------- | ----------------------- | ------------------------- |
| views UNIQUE  | 22.3 / 20.8 с, 0.5 | 21.0 / 19.0 с, 0.5 | 27 / 17 мс, 531    | 946 / 582 мс, 16           | 865 / 558 мс, 17; 0.6 % | 25 / 12 мс, 725; 0.01 %   |
| views TOTAL   | –                  | 27 / 16 мс, 552    | 25 / 16 мс, 585    | 593 / 379 мс, 25           | 537 / 366 мс, 26        | 25 / 11 мс, 742; < 0.01 % |
| referrers TOP | 16.8 / 16.0 с, 0.6 | 1.37 / 1.12 с, 8.5 | 1.25 / 1.12 с, 8.7 | 2.10 с / 766 мс, 10; 6.0 % | 1.11 с / 735 мс, 13     | 116 / 68 мс, 135          |
| durations     | –                  | 27.3 / 24.6 с, 0.4 | 26 / 16 мс, 562    | 739 / 505 мс, 19; 2.4 %    | 661 / 459 мс, 21; 1.3 % | = B, SQL                  |

- Ціль ≤ 300 мс (p95) досягають: A – `TOTAL`; A+ – `UNIQUE`, `TOTAL`, `durations`; C – `UNIQUE`,
  `TOTAL`, `referrers`. B не досягає на жодному звіті, `referrers` не досягає жоден варіант
  MongoDB.
- Прогони v1.0 і сирих звітів A обмежені самим k6: ітерацію, що триває після 30 с, він чекає
  ще 30 с. Встигло по 20 запитів (по два на VU), жоден не обірвано; p95 з 20 значень.
  Звіти v1.0 `TOTAL` і `durations` під навантаженням не міряли (поза протоколом); `durations` A
  – той самий сирий запит, що в v1.0.
- **Помилки B і C – ліміт пам'яті ClickHouse.** За вікно замірів `system.query_log` має 45
  відмов, усі – `Code: 241, Memory limit (total) exceeded … maximum: 1.80 GiB` (90 % від ліміту
  контейнера 2 GiB): через GraphQL 19 `referrers` і 14 `durations`, через SQL 3 `UNIQUE` і 8
  `durations` B та 1 `TOTAL` C (запит, що читає `views_hourly` і край вікна з `records`). Це
  збігається з відмовами k6 поштучно. Через GraphQL помилка приходить у `errors` відповіді 200,
  тож k6 рахує її в `checks`, а не в `http_req_failed`. 3 відмови HTTP під `UNIQUE` C запису в
  `query_log` не мають, їхню причину не з'ясовано. Вибірка –
  `tools/spike-15/results/query-log-errors.tsv` у гілці спайку.
- B через GraphQL повільніший за SQL до 50 мс в одиночних запитах і на 10–90 % під
  навантаженням (`referrers` – удвічі за p95; 6 % його запитів обірвав ліміт пам'яті).

### Сира частина A+ на живому сайті

На стенді дані закінчуються 17.10, тож поточна доба, яку A+ читає з сирих записів, порожня, і
числа A+ для `UNIQUE` – оптимістичні. На живому сайті до півночі сира частина – ціла доба
(`tail-cost.js`, одиночні запити, індекси v1.0):

| Сира частина             | Записів | Медіана, мс | Макс, мс |
| ------------------------ | ------- | ----------- | -------- |
| `UNIQUE`, одна доба      | 166 667 | 330         | 734      |
| `UNIQUE`, одна година    | 6 944   | 8           | 9        |
| `durations`, одна година | 6 944   | 17          | 18       |

Одна доба `UNIQUE` сама по собі вже понад ціль. Під 10 VU її не міряли; оцінка з v1.0
(30 діб – 22.3 с p95) – ≈0.7 с.

Сирі k6-підсумки, таблиці, журнали прогонів і вибірки – гілка `spike/ACKEE-15-clickhouse` у
Voronov/Ackee (архівна, не зливається), `tools/spike-15/results/`.

## Прибрати

```sh
docker compose -f docker-compose.bench.yml --profile seed --profile clickhouse down     # зберегти дані
docker compose -f docker-compose.bench.yml --profile seed --profile clickhouse down -v  # видалити й дані
```

Без `-v` томи `ackee-bench-*` лишаються, і наступний `up -d` піднімає той самий засіяний стенд.
