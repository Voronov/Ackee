# Передача Ackee 4.0 іншій команді

Документ для команди, яка приймає продукт на розвиток і підтримку. Тут описано, що саме передається, як проходить передача знань і коли передачу вважають завершеною. Подробиці винесено в окремі документи, посилання на них наведено нижче.

Версія на момент передачі: **4.0.4** (тег `4.0.4`, live з 19.11.2026). Історія 4.0.1–4.0.4 — у `CHANGELOG.md` і GitHub Releases.

## Документація

Читати в такому порядку:

1. `docs/engineering/architecture.md`: як влаштована система (C4), що лишилось відкритим.
2. `docs/engineering/runbook.md`: щоденна експлуатація, типові проблеми, тестовий трафік.
3. `docs/engineering/deployment.md` і `release.md`: як випускати версію і як відкотитись.
4. `docs/engineering/alerts.md`: алерти, звіти в чат і як їх перевірити.
5. `docs/engineering/ci-cd.md`: перевірки в CI, деплой, бекапи.
6. `docs/engineering/config-matrix.md`: змінні стендів і чим вони відрізняються.
7. `docs/Upgrade guide.md`, `docs/Options.md`: для тих, хто ставить Ackee у себе.
8. `docs/adr/`: чому зроблено саме так, зокрема ADR-004 (чому без ClickHouse).
9. `docs/engineering/benchmark-stand.md`: заміри на 10 млн записів.

## Передача знань (KT)

Чотири сесії по 60–90 хвилин. Кожну веде людина зі старої команди, а практику виконує людина з нової.

| Сесія | Тема                     | Зміст                                                                                         | Практика нової команди                                    |
| ----- | ------------------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 1     | Продукт і демо           | Цілі v2.0, демо на 10 хв (runbook), робочі простори й ролі, звіти, фільтри, експорт, MCP, GA4 | Створити акаунт на dev, додати домен, побачити свій візит |
| 2     | Код і процес             | Структура `src/`, GraphQL-схема, згортки (ADR-005), черга (ADR-006), тести, CI, правила PR    | Невелика зміна в PR через CI до злиття                    |
| 3     | Реліз і відкат           | `release.md`, тег, підтвердження environment, перевірка після деплою, відкат, оновлення з 3.x | Випустити версію на dev і відкотити її                    |
| 4     | Експлуатація й інциденти | Grafana, алерти, звіти в чат, бекапи й відновлення, перебудова згорток, типові проблеми       | Відновити бекап на копії, розібрати штучний збій на dev   |

Записи сесій і питання нової команди додаються в цей документ.

## Відомі проблеми й обмеження

| Що                                                   | Стан                                                                                                                                                                                                                                |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Фільтр по кількох вимірах одночасно читає записи     | Фільтр по одному виміру (реферер, браузер, країна, сторінка…) і години поточного дня беруться зі згорток з 4.0.3–4.0.4: на 10 млн 13–232 мс. Фільтр по двох вимірах, наприклад країна + браузер, читає записи: на 10 млн ≈ 3 хв     |
| Зміна `ROLLUP_VERSION` перебудовує згортки з нуля    | Старі згортки видаляються, і поки триває перебудова, звіти читають записи: live — менше хвилини, 10 млн — 11 хв. Реліз зі зміною версії на великій базі викочувати вночі. Будувати нові згортки поруч зі старими вирішили не робити |
| GA4-звіти без фільтрів                               | Обмеження 4.0.0                                                                                                                                                                                                                     |
| Черга й розділення процесів працюють лише на dev     | Live пише напряму; рішення описано в `architecture.md`                                                                                                                                                                              |
| Один сервер                                          | Падіння VPS зупиняє всі стенди. Бекапи копіюються на окремий сервер                                                                                                                                                                 |
| PR етапу релізу злито без людського рев'ю (#99–#115) | CI зелений, але рев'ю після злиття ще треба зробити                                                                                                                                                                                 |

## Відкриті ризики

| Ризик                                                     | Пропозиція                                         |
| --------------------------------------------------------- | -------------------------------------------------- |
| Секрети знає попередня команда                            | Змінити всі значення `.env` і ключі після передачі |

## Модель підтримки

| Період                 | Хто відповідає                 | Що робить                                       |
| ---------------------- | ------------------------------ | ----------------------------------------------- |
| До дати передачі       | Стара команда                  | Чергує, випускає, відповідає за інциденти       |
| 2 тижні після передачі | Нова команда; стара на зв'язку | Нова чергує, стара відповідає на питання в чаті |
| Після                  | Нова команда                   | Повна відповідальність                          |

Чергування: алерти й звіти приходять у Telegram-групу «Ackee Alerts». Реакція на `critical` — протягом робочого дня. Рішення про відкат приймають Tech Lead і автор релізу (`deployment.md`).

## Критерії завершення передачі

Передачу вважають завершеною, коли нова команда **сама**, без допомоги старої:

- [ ] зібрала й запустила Ackee локально, прогнала тести;
- [ ] злила PR через CI і побачила його на dev;
- [ ] випустила версію на live за `release.md` і виконала перевірку після розгортання;
- [ ] відновила бекап на копії бази й перевірила дані;
- [ ] отримала алерт на штучний збій dev і відновила стенд;
- [ ] змінила секрети з таблиці доступів;
- [ ] відповіла на всі відкриті питання цього документа.

Підписи: від старої команди (Product Owner, Tech Lead), від нової (керівник команди), дата.
