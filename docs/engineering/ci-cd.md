# CI/CD

Кожна зміна потрапляє в `develop` лише через pull request, а PR зливається лише з зеленим CI.
Рев'юера призначає `.github/CODEOWNERS`, і потрібен approve хоча б одного власника змінених файлів
(CI/CD і сервер – Воронов або Пеняка, тести – Громяк або Воронов, решта – будь-хто з команди).
Тут описано, що саме перевіряється і як виходить реліз.

## Перевірки на кожен push і PR

Файл `.github/workflows/test.yml`.

| Job              | Що робить                                                                                                        | Чому                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Test             | `npm run build:pre`, потім `npm test` (ESLint, Prettier, AVA) на Node 24 і 26, Linux і macOS                     | Linux – там працює образ, macOS – там пише команда        |
| Coverage         | `npm run test:coverage`, пороги в `.c8rc.json`; Redis – service container `redis:7.4-alpine`, `ACKEE_TEST_REDIS` | Падіння покриття нижче порогу – це регресія, а не шум     |
| Dependency audit | `npm audit --omit=dev --audit-level=high`                                                                        | Висока вразливість у тому, що їде в образ, зупиняє збірку |

Тести черги прийому (`test/queue/redis.js`, `test/resolvers/ingestQueue.js`) і спільної солі
(`test/utils/salt.js`) ходять у справжній Redis лише тоді, коли задано `ACKEE_TEST_REDIS`. Це
робить тільки job Coverage: service containers є лише на Linux-раннерах. У job Test (Linux і
macOS) ці тести пропускаються (`skip`), а решта, зокрема обхід черги при недоступному Redis,
іде як завжди.

Пороги покриття стоять трохи нижче виміряного значення. Коли покриття росте, пороги піднімають
у тому ж PR.

## Як запустити те саме локально

```
npm ci
npm run build:pre
npm test               # lint + усі тести
npm run test:coverage  # те саме з порогами покриття
```

З тестами, яким потрібен Redis, як у job Coverage. Redis має бути без цінних даних: тести
очищають свої бази.

```
docker run -d --name ackee-test-redis -p 127.0.0.1:6390:6379 redis:7.4-alpine
ACKEE_TEST_REDIS=redis://127.0.0.1:6390 npm run test:coverage
docker rm -f ackee-test-redis
```

## Браузерні тести

`Browser tests` у CI проходять справжній браузер (Playwright, Chromium) по справжньому Ackee, зібраному з цього коміту, з MongoDB і Mailpit для листів. Усе в Docker, команда однакова на ноутбуці й у CI: `docker compose -f e2e/docker-compose.yml run --rm --build tests`. Кожен тест створює власний обліковий запис, тож порядок не важливий.

Що покрито (`e2e/*.browser.js`):

| Файл            | Що перевіряє                                                                                                                |
| --------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `registration`  | реєстрація, лист із посиланням, вхід; непідтверджена адреса; хибний пароль                                                  |
| `passkey`       | додати passkey у налаштуваннях, вийти, увійти ним                                                                           |
| `domains`       | створити домен, id і код вбудовування, перейменувати, видалити; два домени                                                  |
| `reports`       | перегляди з трекера в звітах, власні візити (cookie) не рахуються, невідомий домен                                          |
| `domain-select` | Overview для всіх доменів і для одного                                                                                      |
| `members`       | запросити людину ролі Viewer/Editor, прийняти за листом, права лише на читання, посилання діє один раз, видалення учасника  |
| `tracking`      | правила трекінгу збирають кліки, перегляди, форми, посилання, завантаження, прокрутку; підроблений `document.currentScript` |

Результат дивитися так:

- у запуску на GitHub (вкладка Summary) є таблиця: файл, тест, статус, час;
- артефакт `browser-tests` (14 днів) зберігається для кожного запуску, не лише для невдалого: там `playwright-report/index.html` з відео кожного тесту й трейсами падінь (`npx playwright show-report`);
- сторінка зі звітом останнього злиття в develop: ввімкнути GitHub Pages (Settings → Pages → Source: GitHub Actions) і задати змінну репозиторію `E2E_PAGES=true`; без неї цей крок пропускається.

Подробиці для авторів тестів: ліміт відкриття посилань з листів 30 за 15 хвилин для одного IP (ACKEE-65), тому `createAccount` у `e2e/_helpers.js` підставляє тесту власну адресу в `X-Forwarded-For`, як це зробив би проксі. Node-частина тестів (`request`) не знає ім'я `ackee.localhost`, воно відоме лише браузеру, тому до API вона звертається за `E2E_API`.

## Версії

Нумерація продовжує upstream: робота почалась з Ackee 3.6.1. Зміни без нової поведінки
(якість, рефакторинг) – patch-версії `3.6.x`. Кінець спринту – `4.0.0-alpha.N`, фінал після
всіх спринтів – `4.0.0`: мультитенантність і акаунти несумісні з 3.x, тому мажорна версія.
«Ackee v2.0» – назва проєкту, друга версія нашого продукту; номер пакета від неї не залежить.

## Реліз

1. Тікети не редагують `CHANGELOG.md`: у паралельних гілках це гарантований конфлікт.
2. Реліз – окремий коміт у `develop`: секцію версії збирають із назв злитих PR, той самий
   номер ставлять у `package.json`.
3. `develop` зливають у `master`, на коміт ставлять тег `X.Y.Z`.

## Деплой і smoke-тест

Злиття в `develop` викочується на dev, тег версії – на live після approve (`.github/workflows/deploy.yml`).
Після кожного деплою `.github/scripts/smoke.sh` перевіряє стенд лише читанням:

- сторінка відповідає 200;
- GraphQL-запит `build` відповідає без помилок;
- база даних підключена;
- стенд віддає саме ту збірку, яку задеплоїли (тег версії або `sha-<commit>`; CI вписує її в образ як `ACKEE_BUILD`).
- образ `sha-<commit>` зібрано саме з цього коміту: обидва checkout у `deploy.yml` беруть `github.sha`, а не вершину гілки, і крок «Built commit matches the tag» це перевіряє. Раніше два злиття за хвилину давали образ із тегом першого й кодом другого (ACKEE-78, журнал J-40).

Якщо щось із цього не виконується за ~2,5 хв, запуск Deploy стає червоним. Образ, старший за запит
`build` (відкат на давній тег), перевіряється лише на відповідь API – з попередженням у лозі.

Вручну: `.github/scripts/smoke.sh https://dev.ackee2.varlex.app sha-1a2b3c4`.

Після smoke йде `.github/scripts/smoke-features.sh`: що стенд робить для залогіненого користувача, лише читанням. Тестовий користувач і токен метрик беруться з секретів середовища (`SMOKE_USER`, `SMOKE_PASSWORD`, `SMOKE_METRICS_TOKEN`); без `SMOKE_USER` і `SMOKE_PASSWORD` крок пропускається, тож стенд без тестового користувача (live) не страждає. Перевіряє:

- `ga4Available` (на стенді заданий `ACKEE_SECRET_KEY`);
- помилки синхронізації GA4 в доменах користувача (лише попередження: це відповідь Google, а не поламаний деплой);
- що `/api/live` відповідає `200 text/event-stream`;
- що `/metrics` відповідає 200 з токеном (якщо токен заданий).

Вручну: `SMOKE_USER=... SMOKE_PASSWORD=... .github/scripts/smoke-features.sh https://dev.ackee2.varlex.app`. Токен входу скрипт створює на час запуску й видаляє.

### Compose на сервері

Один `docker-compose.yml` описує обидва стенди, тому його оновлює лише деплой dev. `/usr/local/bin/ackee-deploy` перед перезапуском `ackee-dev` завантажує `deploy/docker-compose.yml` того ж коміту, перевіряє його `docker compose config -q`, кладе стару копію поруч як `docker-compose.yml.bak-<дата>` (лишається 5 останніх) і підміняє файл. Якщо завантаження чи перевірка не вдалися, деплой зупиняється, а стенд лишається як був. Деплой live файл не чіпає: реліз не має переписувати dev, а старі теги (`3.6.x`, відкат) такого файлу не мають. Тому compose на сервері завжди відповідає `develop`, навіть для live, поки там не буде нового релізу; нове в compose для live доїде з наступним деплоєм dev і застосується при перезапуску сервісу.

`ackee-deploy` перезапускає лише `ackee-<стенд>` (`--no-deps`), тож змінні й ліміти доходять самі, а новий сервіс (наприклад `redis-queue`) треба підняти руками: `docker compose up -d <service>`. Скрипт на сервері оновлюється вручну (один раз): `sudo install -m 755 deploy/ackee-deploy /usr/local/bin/ackee-deploy`. Нові змінні в `.env` (ключі, токени) теж вручну.

Чекліст, якщо скрипт на сервері старий: скопіювати `deploy/docker-compose.yml` у `/opt/ackee`, `docker compose config -q`, `docker compose up -d`.
