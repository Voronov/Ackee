# Runbook

Як експлуатувати Ackee 4.0 на сервері `hosting2` і що робити, коли щось ламається. Архітектуру описано в `architecture.md`, розгортання і відкат у `deployment.md`, готовність до релізу в `release.md`.

Усі команди нижче виконуються на сервері в `/opt/ackee`, від root.

## Стенди

| Стенд | Адреса                        | Контейнер    | База         | Що запущено                  |
| ----- | ----------------------------- | ------------ | ------------ | ---------------------------- |
| live  | https://ackee2.varlex.app     | `ackee-live` | `ackee_live` | тег версії, `ACKEE_LIVE_TAG` |
| dev   | https://dev.ackee2.varlex.app | `ackee-dev`  | `ackee_dev`  | `sha-<коміт>` з `develop`    |
| v1    | https://ackee.varlex.app      | `ackee-v1`   | `ackee`      | 3.6.1 для порівняння         |

Grafana: https://grafana.ackee.varlex.app. Prometheus: https://prometeus.ackee.varlex.app (basic auth).

## Змінні оточення

Що означає кожна змінна, описано в `docs/Options.md`. Значення для стендів задано в `docker-compose.yml`, а секрети лежать у `.env` (права 600, у git не потрапляє). Чим стенди відрізняються, показує `config-matrix.md`.

Нову змінну вносять на сервер до деплою, бо деплой live не змінює ні `.env`, ні compose. Перед зміною `.env` треба зробити копію: `cp .env .env.bak-$(date +%Y%m%d-%H%M%S)`.

## Запуск, зупинка, стан

```sh
docker compose ps                              # стан і healthcheck
docker compose logs --since 30m ackee-live     # журнал
docker compose restart ackee-live              # перезапуск з тим самим тегом
docker compose stop ackee-live                 # зупинка (перед відновленням бази)
docker compose up -d --no-deps ackee-live      # запуск
```

Новий тег ставить лише `ackee-deploy`, ним керує workflow `Deploy`. Вручну, якщо Actions недоступний:

```sh
SSH_ORIGINAL_COMMAND="live 4.0.0" /usr/local/bin/ackee-deploy
```

Образ має вже бути в `ghcr.io/voronov/ackee`. Скрипт перевіряє формат тега і записує його в `.env`.

Перевірка після будь-якої дії:

```sh
.github/scripts/smoke.sh https://ackee2.varlex.app 4.0.0   # з копії репозиторію
curl -s -X POST https://ackee2.varlex.app/api -H 'Content-Type: application/json' \
  -d '{"query":"{ build { id version database } }"}'
```

## Бекап і відновлення

`/usr/local/bin/ackee-backup` щоночі о 03:30 UTC знімає `ackee_live` у `/opt/ackee/backups`. Він тримає 14 архівів і перевіряє кожен. Журнал запусків лежить у `/var/log/ackee-backup.log`, кожен запуск дає рядок `OK` або `FAILED`.

```sh
tail -3 /var/log/ackee-backup.log     # чи пройшов останній
/usr/local/bin/ackee-backup           # бекап зараз, наприклад перед релізом
```

Відновлення повертає дані на час бекапу, і все, що прийшло після нього, пропадає. Тому його роблять лише тоді, коли пошкоджено дані.

```sh
docker compose stop ackee-live
docker exec -i ackee-mongo mongorestore --archive --gzip --drop --nsInclude='ackee_live.*' < backups/<архів>
docker compose up -d --no-deps ackee-live
```

Архів версії 4 містить усі колекції, тому `--drop` достатньо. Для архіву версії 3 спершу видаляють базу цілком (`docs/Upgrade guide.md`).

## Черга прийому

Працює, лише якщо задано `ACKEE_INGEST_QUEUE` (зараз тільки на dev). Без черги цей розділ не потрібен.

| Що видно                                      | Що це означає                                   | Дія                                                                        |
| --------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| `ackee_ingest_queue_oldest_age_seconds` росте | воркер не встигає або стоїть                    | журнал процесу, `docker compose restart ackee-dev`                         |
| `ackee_ingest_fallback_total` росте           | Redis недоступний або повний, запис іде напряму | `docker compose ps redis`, `docker exec ackee-redis redis-cli info memory` |
| `ackee_ingest_queue_dropped_total` росте      | подію не вдалось записати після повторів        | журнал, дефект                                                             |

Поки чергу не прочитано, згортки не будуються. Звіти лишаються правильними, бо читають записи, але працюють повільніше.

## Згортки

Фонове завдання будує їх кожні 10 хвилин. У журналі після кожного запуску є рядок `Rollups cover <від> to <до>`, і дата «до» має бути не старшою за кілька годин.

**Не будуються.** У журналі `Could not build rollups` або `Skipping rollups`. Звіти правильні, але повільні. Треба перевірити MongoDB і чергу.

**Перебудувати з нуля** (наприклад, коли цифри звітів не збігаються з записами):

```sh
docker compose stop ackee-live
docker exec ackee-mongo mongosh --quiet ackee_live --eval \
  '["rollupstates","viewrollups","dimensionrollups","dimensiondayrollups"].forEach(c => db[c].drop())'
docker compose up -d --no-deps ackee-live
```

Після старту завдання будує згортки всіх записів. На 1 млн записів за 180 днів це зайняло 28 с (локально, M4 Pro). Поки воно працює, звіти читають записи.

## Типові проблеми

| Симптом                                        | Перевірити                                                    | Дія                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Стенд не відповідає                            | `docker compose ps`, `logs`, `free -m`                        | Перезапуск. Якщо падає знову, відкат за `deployment.md`                                   |
| Контейнер у циклі рестартів, `mongo` unhealthy | `df -h /`: колись диск був заповнений на 100 % (12.10)        | `docker builder prune`, старі образи, логи. Потім перезапуск                              |
| Немає нових переглядів                         | Консоль браузера на сайті, CORS, ключ прийому, `strictIngest` | `ACKEE_ALLOW_ORIGIN`, сніпет з ключем, `docs/Options.md#ingest-key`                       |
| Вхід не працює                                 | Журнал: `loginattempts`, ліміт спроб                          | Почекати ліміт. Пароль адміністратора задано в `.env` (`ACKEE_USERNAME`/`ACKEE_PASSWORD`) |
| Листи не приходять                             | Журнал при старті: перевірка SMTP                             | Змінні `ACKEE_SMTP_*` стенда                                                              |
| GA4 без даних                                  | Журнал синхронізації, `ACKEE_SECRET_KEY` того самого стенда   | Підключення GA4 знову в Settings                                                          |
| Звіт з фільтром повільний                      | Очікувано, близько 4 с на 10 млн                              | Відоме обмеження 4.0.0                                                                    |
| Немає бекапу за ніч                            | `/var/log/ackee-backup.log`, вільне місце (потрібно ≥ 2 ГБ)   | Звільнити місце, запустити `ackee-backup` вручну                                          |

## Моніторинг

Метрики стендів читає Prometheus з токеном стенда. У Grafana три дашборди: сервер, контейнери, застосунок. Що дивитись після релізу: час відповіді `ackee_http_request_duration_seconds`, частку 5xx, рестарти контейнера, вільне місце на диску, рядок `Rollups cover` у журналі.

## Передача знань

**Демо-сценарій (10 хвилин).** Вхід на live. Overview за 30 днів. Клік по рефереру ставить фільтр, адреса зберігає фільтр і період. Експорт картки в CSV. Countries з картою. Insights → Live: відкрити сайт у другій вкладці, і візит з'являється. Settings: робочий простір, запрошення з роллю Viewer, світла тема. MCP: запит «скільки переглядів вчора». Наприкінці показати Grafana і журнал бекапів.

**Відомі обмеження 4.0.0.** Фільтрований звіт читає записи. ClickHouse не ввімкнено. GA4 без фільтрів. Черга й розділення процесів працюють лише на dev. Країни не ввімкнено на жодному стенді.

**Відкриті ризики.** Один сервер без резерву: падіння VPS зупиняє всі стенди, а бекапи лежать на тому самому диску. Диск заповнений на 87 %. Dev і live мають спільний пароль адміністратора. Немає зовнішнього каналу сповіщень, доки не встановлено алерти (ACKEE-111).
